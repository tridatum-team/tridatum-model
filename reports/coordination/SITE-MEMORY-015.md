# SITE-MEMORY-015 — 같은 기능·수치를 유지하는 메모리 낭비 조사

**상태: 원인 조사 완료, 한계 확인. 코드 변경 없음.**
- 측정된 사용량의 대부분은 꼭 필요한 가중치와 색인 객체다.
- 같은 수치를 보장하면서 줄일 수 있는 양은 **최대 약 0.4GB(상시)와 약 0.8GB(기동 순간 최고치)** 이다.
- 맥미니 질의 부하에 필요한 작업 집합 하한은 **약 5.6–6.0GB** 이다. 맥미니 유휴 시 쓸 수 있는 메모리 4.0–4.5GB보다 크다.
- 그래서 정확성 유지 수정만으로는 이관 조건을 채울 수 없다. 수정은 하지 않았고, 아래에 근거와 선택지를 남긴다.
- 사이트는 맥북 그대로, Docker VM은 정지 상태 그대로다. 다른 서비스는 손대지 않았다.

## 1. 측정 방법

- 맥미니(대상 기기)에서 배포판 `9256df4` 로더를 **구성 요소별로 따로 짧은 프로세스**로 띄웠다.
- 각 단계의 RSS와 최고치(`ru_maxrss`)를 쟀다. 압력 가드를 썼고, 세 번 모두 압력은 1이었다.
- llama-server는 띄우지 않았다(별도 LLM 서버 동시 기동 없음).
- 맥북 라이브 백엔드(pid 72632, 같은 배포판)는 `vmmap`으로 읽기만 했다. 익명 메모리와 파일 매핑을 나누는 데 썼다.

## 2. 구성 요소별 실측 (맥미니, 2026-11-01)

| 구성 요소 | 상시 RSS (자기 몫) | 기동 최고치 | 근거·메모 |
|---|---|---|---|
| Python + numpy + torch | 0.19GB | — | |
| 추출 독해기 (`trid/extractive.load_reader`) | 0.36GB | **0.88GB** (+0.33 일시) | 가중치 0.342GB. 모델을 무작위 초기화로 만든 뒤 `load_file`로 한 벌 더 읽고 `load_state_dict`로 복사하는 동안 두 벌이 된다 |
| Workspace v5 (`Index.load` + 메타·색인 구조) | 1.30GB (Index.load +1.20) | **2.28GB** (+0.78 일시) | dense float32 0.397GB(f16 파일 → float32 변환, 변환 순간 f16 0.2GB가 함께 있음). 검토 파일 74MB를 통째 문자열로 읽어 줄로 나눔(일시). 104,134 문단의 파이썬 객체 |
| Workspace inst-reb-002 | 0.07GB | — | 임베더를 공유한다(중복 없음, 코드 확인) |

**맥북 라이브 백엔드 vmmap**(physical footprint 2.7GB, 최고 2.9GB)
- 파이썬 객체: `MALLOC_SMALL` 0.60GB + pymalloc arena(`VM_ALLOCATE` 757개, 0.75GB).
- 큰 버퍼: `MALLOC_LARGE` 1.1GB. dense float32 0.4GB, 독해기 가중치 0.34GB, 긴 문단 문자열 등.
- `IOAccelerator` 0.24GB: 출처 미확인. torch의 Metal 장치 초기화로 보인다 [추정].
- 지금 맥북에서는 전부 스왑 상태다.

## 3. 같은 수치를 보장하는 절감 후보 (구현 안 함)

| 후보 | 방법 | 절감 | 같은 수치 근거 |
|---|---|---|---|
| A. 독해기 적재 복사 | `load_state_dict(..., assign=True)` | 최고치 −0.33GB, 상시 0 | 같은 텐서를 그대로 쓴다 |
| B. dense 변환 순간 f16 | `np.load(mmap_mode='r')` 후 `astype(float32)` | 최고치 −0.2GB | 같은 float32 배열 |
| C. dense float32를 파일 매핑으로 | f16에서 정확히 변환한 float32 파일을 만들어 mmap | 상시 익명 −0.4GB(질의 때는 여전히 전부 상주) | 같은 값, 같은 행렬 곱 호출. 파생 파일 0.43GB와 출처 sha 검사가 필요하다 |
| D. 검토 파일 통째 읽기 | 줄 단위로 읽기 | 최고치 −0.2~0.3GB [추정] | 같은 줄을 같은 순서로 읽는다 |

- **합계:** 상시 익명 최대 −0.4GB, 기동 최고치 최대 약 −0.8GB.
- **줄일 수 없는 것**(수치·기능 유지 조건)
  - bge-m3 float32 가중치 2.1GB(이미 mmap).
  - Q8_0 1.7B 1.8GB와 KV.
  - 색인 파이썬 객체 약 1.3GB. 줄이려면 색인 구조를 대규모로 다시 써야 해서 금지 범위다.

## 4. 맥미니 이관 하한

| 항목 | GB |
|---|---|
| 질의 시 작업 집합 (기본 + 독해기 + 워크스페이스 2개 + 임베더 + llama) | 0.19 + 0.36 + 1.37 + 1.85 + 2.24 ≈ **6.0** |
| 위 절감 A–D를 모두 적용 | ≈ **5.6** (최고치는 약 0.8 더 낮음) |
| 맥미니 유휴 시 쓸 수 있는 메모리 (free + inactive, Docker VM 정지 후 실측) | **4.0–4.5** |

- 차이는 1GB 이상이다. 질의 때마다 bge-m3 2.1GB와 Q8_0 1.8GB를 모두 거치므로, 파일 매핑이어도 상주해야 하는 양이다.
- SITE-MIGRATION-013/014 실측(기동 7–10초에 압력 2, Metal 질의 중 압력 2)과 맞는다.

## 5. 구현하지 않은 이유

- A–D는 같은 수치를 지키지만 이관 하한을 넘지 못한다.
- 배포판은 `9256df4` 고정이다. 작업 트리의 `scripts/shared_demo.py`에는 검증 전 ROOT-009 변경이 섞여 있다.
- 메모리 수정을 배포하려면 `9256df4` 기반으로 따로 커밋하고 같은 질문 결과 비교와 C 확인을 거쳐야 한다.
- 효과가 목표에 못 미치는 변경을 그 절차까지 밀어붙이지 않았다.
- 총괄이 맥북 원점 메모리 여유용으로 원하면, A와 D부터(가장 작고 정확성 위험이 없음) 별도 커밋으로 진행할 수 있다.

## 6. 정확도·기능 trade-off가 필요한 선택지 (사용자 결정, A는 실행하지 않음)

| 선택 | 절감 | 영향 |
|---|---|---|
| bge-m3 CPU float16 | 약 −1.05GB | 질문 벡터 수치가 바뀌어 검색 순위가 달라질 수 있다. C 재검증 필요 |
| 컨텍스트 4096 → 2048 | KV 약 −0.24GB [계산] | 긴 근거가 잘린다. 답변 계약이 바뀐다 |
| 더 낮은 양자화(Q4 등) | 약 −0.8GB | 모델 변경이다. 금지 범위라 사용자 결정 |
| 더 큰 RAM 기기 또는 다른 호스트 | — | M4 맥미니는 RAM 증설 불가. 기기 교체 |
| 맥북 원점 유지 | — | 현재 작동 중 |
