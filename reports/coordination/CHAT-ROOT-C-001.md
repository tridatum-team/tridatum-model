작성: C, 2026-11-02. 기존 공개 기록·코드만 읽었다. 새 추론·실패 재현·테스트·학습·수집·인스턴스 기동·운영 변경 모두 0.

## 1. 결론과 이전 판단 정정

**확정된 것은 현재 생성 구성에서 일반 대화 실패가 발생한다는 사실이다. 모델 가중치 자체, 모델 크기, 학습량 부족이 원인이라는 결론은 아직 없다.**

- 총괄 운영 실측의 메일 다듬기 실패는 검색 없는 일반 대화에서 발생했다. 따라서 그 사례는 RAG 범위·미수집 자료로 설명할 수 없다. 확인 요청을 확정으로 바꾸고 요청에 없는 문장을 추가한 것은 의미 보존 실패다. 재실행하지 않았다.
- GENERAL-CHAT-003은 system 내용과 일부 디코딩만 바꿨다. 모든 팔에 같은 Q8_0 GGUF, llama.cpp, native template, `enable_thinking=False`, 고정 history가 공유됐다. 이 공유 조건을 분리하지 않았으므로 **“모델 능력 문제이며 교체로만 해결”은 근거보다 강하다.**
- 최소 역할·system 없음에서도 실패가 남았으므로 현재 `CHAT_SYSTEM` 문구가 모든 실패의 유일한 필요 원인이라는 설명은 약해진다. 그렇다고 모든 프롬프트 설계나 서비스 구성의 가능성을 배제한 것은 아니다.
- `MODEL-RESUME-C-030.md`의 “대화는 가중치 수준 변화 필요 가능성이 높음”, “E1 전 미세조정/다른 접근 보류”를 원인 확정이나 다음 진단의 선행 조건으로 쓰지 않는다. **E1은 후보의 운영 적합성 평가이지 현재 실패의 원인 분리 실험을 대체하지 않는다.**
- `2b8ba92`의 국내·국외 후속 승계 배포는 검색 경로 개선이다. 일반 대화 개선 증거가 아니다.

## 3. 현재 배포까지의 변경분과 A 교차

### 코드 변경분 — 실행 없이 비교

`9256df4`, `6a5eb37`, `2b8ba92`의 `scripts/shared_demo.py`에서 다음 정의를 AST로 비교했다. 모두 동일했다:

`CHAT_SYSTEM`, `CHAT_SAMPLING`, `HISTORY_MESSAGES`, `_messages`, `chat_complete`, `chat_reply`, `conversation_turns`.

따라서 핵심 생성 함수가 바뀌었다는 증거는 없다. 이것은 현재 프로세스의 바이너리·실효 서버 설정을 다시 측정한 결과는 아니며, 라우팅 및 전체 세션 처리 코드까지 모두 같다는 뜻도 아니다.

현재 후보 코드에서 읽힌 공통 경로:
- `chat_complete`: native template + `enable_thinking=False`, 서비스 sampling, 무작위 seed.
- `chat_reply`: 기본 384토큰, 첫 턴 안내 추가, 컨텍스트 부족 시 오래된 user/assistant 쌍 제거, 숫자가 든 일부 업무 주장 후처리.
- 세션 기록: 대화 답은 화면에 보인 후처리 결과를 최대 1500자로 저장, 총 24개 메시지 유지. 따라서 화면 답·history·원시 생성문은 항상 같다고 가정하면 안 된다.
- 이 저장/후처리가 최신 메일 의미 변경의 원인인지는 원시 생성문과 최종 표시의 쌍이 없어 미확정이다. 검색이 없었다는 총괄 실측은 그대로 수용한다.

## 4. 왜 대화 개선이 지연됐나 — 확인 가능한 프로세스 원인

1. **진단을 너무 빨리 모델 선택 문제로 좁혔다.** C030은 공유 조건을 분리하지 않은 실험에서 가중치 변경 가능성을 높게 잡고, 대화를 세 번째 우선순위로 뒀다. “생성 결과가 틀림”과 “가중치가 원인”을 구분했어야 한다.
2. **다음 판단을 새 AWS E1 환경에 직렬로 묶었다.** 후보 적합성 평가의 환경 구축이 현재 경로 진단의 선행 조건이 됐다. A034에 따르면 smoke 두 번은 Python setup에서 실패했고 추론은 0이다. 비용을 쓰면서도 대화 원인에 관한 새 정보는 얻지 못했다.
3. **검색 개선과 별도 후보 개발을 운영 일반 대화 진전으로 혼동할 위험을 방치했다.** 검색 조건 배포는 해당 생성 함수를 바꾸지 않았다. CHAT-CAPABILITY-005의 system 후보는 Gemma raw 모드 전용이며, 공개 20 반복 결과를 운영 원본의 개선 증거로 전용할 수 없다.
4. **휴리스틱 수치를 의미 판정으로 요약했다.** BASELINE-COMPARE-002는 `BASELINE-SEMANTIC-001` 정정에서 제약 추천 위반/답 부실을 분리했다. 다른 모델 비교도 세대·양자화·디코딩·자기 history가 함께 달라 크기 인과를 입증하지 못한다.

이는 기록으로 확인되는 지연 구조다. 일주일 전체의 각 작업 시간·담당자 대기 시간을 재구성한 것은 아니다. C의 잘못은 원인 분리 전에 E1을 일반 대화 개선의 필수 관문처럼 둔 판단이다. 수집량·모델 크기·학습량을 미확인 원인으로 추가하지 않는다.

## 5. 최소 비교 실험안 — 제안만, 지금 실행하지 않음

**우선 선택: 같은 모델에서 non-thinking 공유 조건을 분리한다.** 기존 GGUF를 사용하는 제한된 로컬 실험을 별도 승인 후 수행하는 안이다. 새 GPU/CPU 인스턴스, 운영 mini 변경, 기존 실패 문장 재실행, 공개 20 사용은 필요 없다. 로컬 파일 존재만으로 안전 실행 가능하다고 단정하지 않으며, 실행 환경·자원 여유는 A와 사전 확정한다.

### 1단계: mode 한 변수, 최대 4회 생성

- 새 공개 입력 2개만 작성·동결한다: (a) history 없는 의미 보존 다듬기, (b) 짧고 정합적인 고정 history에서 원문 조건을 보존하는 후속 수정. 기존 실패 문장을 단어만 바꿔 재현하거나 공개 20을 가져오지 않는다.
- 각 입력을 `enable_thinking=False` / `True` 두 팔로 1회씩. 같은 GGUF·runtime·system·history·seed·sampler·전체 토큰 상한을 사용한다. thinking template 접두 변경은 의도한 처치다. 이미 검증한 template parity를 다시 측정하지 않는다.
- 전체 출력 상한은 두 팔 동일한 진단 예산(예: 1024토큰)으로 사전 고정한다. 운영 384토큰과 다른 실험이라는 점을 명시한다. reasoning 소모로 최종 답이 없거나 잘리면 내용 실패와 분리해 “예산 내 판정 불가”로 기록한다. 내부 사고문은 보고·영구 로그에 남기지 않고 최종 답·사용량·stop만 제한적으로 보관한다.
- mode별 권장 sampler까지 동시에 바꾸지 않는다. 이는 고정 sampler 아래 mode의 영향만 보는 실험이지 각 mode의 최적 품질 비교가 아니다.
- 의미 판정 항목을 생성 전 동결한다: 요청↔확정의 발화 기능, 주체, 조건·기한·사실 보존, 새 정보 추가 여부, 요청된 형식 변경 수행. 팔 이름을 가린 최종 답을 의미로 판정한다. 키워드·유사도 통과를 정확도로 쓰지 않는다.
- 한 팔만 정상이어도 그 입력에서 설정 영향이 있다는 반례일 뿐 통계적 개선·배포 승인·원인 단독 확정은 아니다. 둘 다 실패해도 모델 크기/학습량 원인으로 넘어가지 않는다. seed 안정성 평가나 튜닝을 자동 추가하지 않는다.
