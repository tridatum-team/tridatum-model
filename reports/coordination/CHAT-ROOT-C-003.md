# CHAT-ROOT-C-003: 원모델 reference와 GGUF 경로 분리 실측

작성: C, 2026-11-02. 사용자의 추가 확인 없이 계속 진행하라는 지시에 따라 로컬에서 실행했다.

## 1. 결론

**동일 입력의 의미 누락이 원모델 BF16 경로에도 남았다. 이 사례를 Q8 변환이나 llama.cpp만의 결함으로 설명할 수 없다. 그러나 모델 크기·학습량·가중치만이 원인이라고 확정하지도 않는다.**

- 확인 요청은 HF/GGUF의 greedy 최종 답이 글자까지 같고 의미를 보존했다.
- 확정 진술은 두 경로 모두 검토 완료 사실을 빠뜨렸다. GGUF는 원문에 없는 확인 요청, HF는 원문에 없는 안심 표현과 다른 문자를 추가했다.
- 이어서 대화 역할을 편집 역할로 교체하는 후보와, system은 유지한 채 지시/원문 경계만 명시하는 후보를 각각 한 번씩 비교했다. 추가 요청은 사라졌지만 사실 누락은 남았다. 둘 다 채택하지 않았다.
- **생산 코드·운영 변경 0. 개선 완료 또는 배포 가능 판정이 아니다.** 해당 기준을 충족하지 못한 후보를 실적을 위해 적용하지 않는다.

## 3. 원모델 비교 설계와 결과

### 조건

- 기존 로컬 자산만 사용: 원본 `Qwen3-1.7B-Q8_0.gguf`와 `qwen3-1.7b-hf-rev70d244cc` 원모델.
- Transformers 5.21.0 / torch 2.14.1 / Python 3.12.13. HF는 checkpoint 원래 BF16, CPU eager attention. GGUF는 기존 llama.cpp `8ca4060` CPU.
- 같은 고정 system·첫 턴 안내·질문을 canonical tokenizer로 한 번 token ID 배열로 만들고 **그 배열을 그대로 두 엔진에 전달**했다. HF/GGUF template parity를 새로 반복 평가한 것이 아니다.
- 양쪽 non-thinking, greedy, presence/frequency penalty 0, repetition penalty 1, 최대 새 토큰 384, 입력+출력 context 4096 이내. HF eos IDs 151645/151643 사용. 두 경로 모두 eos로 끝났다.
- 이전 서비스 sampling의 seed를 두 라이브러리에서 같게 설정하는 것만으로는 동등한 추출이 되지 않는다. 그래서 이번 엔진 비교는 양쪽 greedy로 통제했다. 서비스 `.7/.8/20/presence1.5`와 같은 실행이라고 주장하지 않는다.
- BF16는 원모델 경로이며 FP32 reference 성공으로 보고하지 않는다. FP32의 안전 중단 후 **메모리를 줄이는 구현 변경**을 명시하고 BF16만 추가 실행했다.

### 사전 고정 의미 기준에 따른 결과

| 공개 입력 | GGUF CPU greedy | HF CPU BF16 greedy | 결론 |
|---|---|---|---|
| 외부 공유 여부 검토 요청 + 검토 전 공개 금지 | 요청·금지 보존 | 같은 최종 문자열, 요청·금지 보존 | 두 경로 통과 |
| 외부 공유 검토 완료 + 공유 승인 사실 | 검토 완료 누락, “확인해 주세요” 추가 | 검토 완료 누락, “放心해요”라는 안심·혼합 문자 추가 | 두 경로 부분 충족, 전체 통과 아님 |

검토 요청 출력은 양쪽 33토큰이었다. 확정 진술은 GGUF 32, HF 30토큰으로 길이 한도에 도달하지 않았다. 따라서 이 출력에서 누락을 토큰 잘림으로 설명할 근거는 없다.

**분리 범위:** 같은 소스 계열·같은 token IDs·같은 greedy라도 양자화/변환/attention 수치 경로/엔진 구현은 함께 다르다. 토큰별 logits 동등성을 시험하지 않았다. 출력이 다른 것은 관측됐지만 Q8 또는 llama의 특정 버그를 입증하지 않는다. 원모델에서도 같은 사실 누락이 남았다는 반례는 확보했다.

## 4. 후속 개선 후보 두 개 — 운영 적용하지 않음

C002의 서비스 sampling baseline을 재사용했다. 각 후보에서 새로 생성한 것은 두 건뿐이며, 좋은 seed를 고르거나 원문을 바꾸지 않았다.

### A. 대화 역할 대신 편집 역할

C002의 의미 보존 지시 **추가**와 달리, 공감·자연스럽고 구체적인 대화 역할 자체를 원문 편집 역할로 대체했다. first-turn 안내·sampling·질문은 그대로다.

- 확인 요청: 의미는 보존했지만 원문의 “부탁해요”까지 거의 그대로 나왔다. 문체 개선까지 충분하다고 주장하지 않는다.
- 확정 진술: 추가 확인 요청은 없어졌으나 검토 완료 사실은 여전히 빠졌다.
- 결론: 문구를 더 추가하는 방향으로 반복하지 않는다. 전체 의미 보존 조건 미충족으로 미채택.

### B. 지시와 편집 대상 원문의 입력 경계

system은 원래 서비스 system으로 유지했다. 기존 공개 입력의 콜론 앞 지시와 뒤 원문을 다음처럼 구분한 사용자 메시지로만 바꿨다.

```text
작업 지시:
[원래 지시]

편집 대상 원문:
<source_text>
[원래 원문]
</source_text>
```

- 확인 요청: 요청·검토 전 금지 보존.
- 확정 진술: 검토 완료 사실 누락. 편집 역할 후보와 최종 답이 같았다.
- 결론: 이 입력 경계 표기만으로 해결되지 않았다. 콜론 파서나 새로운 편집 라우터를 생산 코드에 추가하지 않았다.

## 5. 이번에 좁힌 것 / 남은 것

### 좁힌 것

- 최근 공개 변형의 확정 진술 오류는 **생성 단계**에서 직접 관측됐다. UI나 RAG 없이도 발생한다.
- 이 조건의 사실 누락은 GGUF/Q8 전용 현상이 아니다. 원모델 BF16에서도 발생한다.
- 이 두 출력의 길이 한도 도달은 원인이 아니다.
- 단순 thinking 전환(C002), 지시 추가(C002), greedy 전환, 편집 역할 대체, 원문 경계 표기 가운데 지금 채택할 완전한 수정 근거는 없다.

### 남은 것과 판단 제한

- 같은 원본의 모든 프롬프트/디코딩/과업에서 실패한다는 증명이 아니다. 확인 요청은 정상 처리됐다.
- 모델 크기·학습량 부족·미수집 자료를 원인으로 단정하지 않는다. 후보 선택/학습 필요성을 이 작은 표본으로 결정하지 않는다.
- 팔 이름을 알고 한 C의 직접 의미 판정이다. 독립 블라인드·통계적 개선 주장은 없다.
- 두 문항에 반복적으로 지시를 맞추는 것은 원인 분리보다 개발 세트 맞춤이 되기 쉬워 **여기서 이 두 문항 대상 문구 실험을 종료**한다.
- 배포 가능한 코드 수정은 아직 확보하지 못했다. 없었던 개선을 만들어 보고하거나 안전하지 않은 변경을 운영에 올리지 않는다.
