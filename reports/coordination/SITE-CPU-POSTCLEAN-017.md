# SITE-CPU-POSTCLEAN-017 — 정리 후 상태에서 CPU 전용, 전송 없음 단일 시험

**상태: 현재 허용 범위에서 압력 1 운영 기준 미달.**
- 시험은 1회만 했다. 기동은 통과했지만 **안정화 시작 1초 뒤(18:38:56) 압력 2**가 났다.
- 질문 단계는 실행하지 못했다. 재시도나 다른 설정 조합은 하지 않았다.
- 원점은 맥북 그대로이고, 다른 서비스를 더 끄거나 기준을 낮추지 않았다.

## 1. 조건 (CPU-014와 다른 점)

- **맥미니 상태:** ARDAgent 재시작(SITE-MIGRATION-012), Docker VM 정지(013), bohun-test 중단(016).
- **전송 없음:** 시작 직전 확인했다. 맥북과 맥미니 모두 scp, rsync, 전송 스크립트가 없었다.
- **같은 것:** 배포판 `9256df4`, Qwen3-1.7B Q8_0 `061b54da…`, llama.cpp `8ca4060`, ctx 4096, `-np 1 -t 4 -tb 4 --jinja`, 임베더 bge-m3 float32, 같은 색인. 버전은 `versions-stage1.json`(기본 + 독해기).
- **CPU 전용:** llama.cpp 환경 변수만 썼다(`LLAMA_ARG_DEVICE=none`, `LLAMA_ARG_N_GPU_LAYERS=0`). 격리 포트 51973.
- **기준선(18:38):** 압력 1, free 60%. 로컬 8000=200, 8010=401, 8501=200, 8502=200, 18765=403, 8766=403, 9999=401.

## 2. 실행 장치 확인 (실행 중 llama-server pid 238)

- **인자:** `llama-server -m runs/open-weight-base/Qwen3-1.7B-Q8_0.gguf --host 127.0.0.1 --port 51912 -c 4096 -np 1 -t 4 -tb 4 --jinja` (배포 코드 그대로, `-ngl` 없음).
- **환경:** `LLAMA_ARG_DEVICE=none LLAMA_ARG_N_GPU_LAYERS=0` (`ps eww`).
- **메모리 지도(vmmap):**
  - `IOAccelerator` 64K(Metal 버퍼 없음). Metal 실행 때는 wired가 +2.2GB였다.
  - GGUF `mapped file` 1.8G(상주 1.5G). CPU가 파일 매핑으로 가중치를 읽는다.
- **wired:** 시험 내내 2.74–2.78GB로 그대로였다. GPU offload가 0이라는 실측 근거다.

## 4. 해석

- **CPU-014와 같은 양상이다.**
  - 기동 때 백엔드(임베더 + 색인)와 llama가 약 4.0–4.5GB를 올린다.
  - free가 바닥(0.05GB)나면 시스템이 다른 프로세스를 압축해 압축기가 3.4 → 6.6GB로 늘고, 압력 2가 된다.
- **ARDAgent, Docker VM, bohun-test 정리는 스왑을 21.2 → 3.5GB로 줄였지만 시작 시점 free + inactive는 약 3.9GB였다.** 이 구성의 작업 집합을 압력 1로 담기에는 부족했다.
- **교란 요인(본인 기록):**
  - 실행 장치를 확인하려고 18:38:46–55에 llama-server에 `vmmap`을 실행했다. 압력 2 직전 구간과 겹친다.
  - `vmmap`은 대상 프로세스 메모리를 읽기만 하지만 영향이 0이라고 단정하지 않는다 [추정: 작음].
  - 압축기 증가는 그 전인 18:38:45–52 적재 구간에서 이미 3.36 → 5.99GB로 시작됐다.
- **SITE-MEMORY-015 합산(약 5.6–6.0GB)은 엄밀한 하한이 아니다**(총괄 지적대로 파일 공유와 순차 단계 미반영). 이번 결과는 "현재 허용 범위의 시험 구성에서 압력 1 운영 기준 미달"로만 말한다.

## 5. 정정 반영
