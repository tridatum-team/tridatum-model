# SITE-CPU-TRIAL-014 — 맥미니 CPU 전용(Metal 오프로드 끔) 서비스 시험

**상태: 차단.**
- CPU 전용 설정은 의도대로 작동했다. wired 증가가 사라졌다.
- 그러나 최소 구성 **기동 7초에 압력 2**가 났다. 질문을 보내기도 전이다.
- 시험은 한 번만 했다(같은 실패 반복 없음).
- 그래서 질의 지연, 전체 5버전 CPU 구성, 문서 첨부 시험, 이관은 하지 않았다.
- 원점은 맥북(Metal) 그대로다.

## 1. 바꾼 것과 바꾸지 않은 것

**바꾼 것: llama.cpp 자체 실행 설정(환경 변수)만.**
- `LLAMA_ARG_DEVICE=none` (도움말: "none = don't offload"), `LLAMA_ARG_N_GPU_LAYERS=0`.
- 배포판 `9256df4` 서비스는 llama-server를 `-ngl` 없이 띄우므로 환경 변수가 그대로 적용된다. 코드 변경은 0이다.
- 기본값(설정 없음)은 기존처럼 Metal이다.

**같은 것**
- Qwen3-1.7B Q8_0 `061b54da…`, llama.cpp `8ca4060`.
- 컨텍스트 4096, `-np 1`, 스레드 4, `--jinja`, 시스템 프롬프트·템플릿·샘플링·출력 한도는 배포판 코드 그대로.
- 임베더 bge-m3(원래 CPU float32)와 색인은 그대로다. 질문 특례와 재시도는 없다.

**격리**
- 맥미니 `~/Services/trid-site`, 백엔드 포트 51973(라이브와 다른 포트), 별도 런타임 `.runtime-cpu`.
- 버전은 `versions-stage1.json`(기본 1.7B + 추출 독해기).

**006 블라인드 AWS 평가에는 영향이 없다.** 그쪽 모델, 설정, 실행기는 손대지 않았다.

## 3. 해석

**CPU 전용 확인**
- wired가 2.75–2.78GB로 그대로였다. Metal 시험(SITE-MIGRATION-013)에서는 2.76 → 4.93GB로 늘었다.
- 이 차이가 Metal 버퍼 증가가 없어졌다는 실측 근거다.
- llama 로그 기본 상세도에는 층 오프로드 줄이 없어, 이 판단은 wired 실측에 근거한다.

**차단 원인**
- 압력 2는 llama가 아니라 **백엔드 적재(임베더 bge-m3 float32 약 2.3GB + 색인과 데이터) 단계**에서 났다.
- TRID RSS 3.4–4.3GB가 올라오는 동안 free가 0.05GB로 바닥나고, 다른 프로세스를 압축해 압축기가 3.4 → 6.4GB가 됐다.
- 즉 맥미니의 **유휴 시 여유 물리 메모리가 TRID 백엔드 하나를 올리기에도 모자란다.** Metal을 끄면 llama 쪽 wired 증가만 줄어든다.
- SITE-MIGRATION-013의 Metal 시험에서는 같은 기동이 압력 1로 지나갔다. 그때는 free 0.88 + inactive 3.57GB, 이번에는 0.88 + 3.16GB였다. 시작 시점 여유가 조금 적었고, 둘 다 경계선에 있다 [추정].

## 4. 하지 않은 것과 이유

- 질의 지연 비교(인사, 기관 업무 질문, 일반 규정 질문, 문서 첨부 `/api/sample`) — fixture를 준비했으나 기동 단계에서 정지했다.
- 전체 5버전(LLM 3) CPU 구성 — 최소 구성이 통과하지 못했다.
- 트래픽 전환 — 보고 후 총괄 판단 사항이다.
- docs의 서빙 장치 표시 변경
  - `deploy/shared-demo/versions.json`의 "llama.cpp 8ca4060 Metal"과 `docs/SHARING.md` 표의 서빙 장치 표기.
  - CPU 원점으로 전환한다면 실측에 맞게 CPU로 바꿔야 한다. 이번에는 전환하지 않았으므로 기록만 한다.
