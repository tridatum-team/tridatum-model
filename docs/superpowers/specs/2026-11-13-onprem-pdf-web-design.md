# 고객 내부망 설치형 PDF 근거 확인 웹 서비스 설계

작성일: 2026-11-13 · 상태: 사용자 검토 대기

## 의도

테스트 사이트(`scripts/shared_demo.py`, test.tridatum.co)에서 이미 동작하는 **"PDF를 넣고 근거를 확인하는" 기능**을 고객 기관의 내부망 서버에 바로 설치해 쓰는 웹 서비스로 묶는다. 사용자는 기관 **내부 직원**이고, 직원이 PDF를 올려 질문하면 문서 안 원문 구간과 함께 답을 확인한다. 설치는 Docker로 하고, 서비스 자체에 로그인·권한과 이용 기록이 있어야 한다.

## 목표

- 인터넷 없는 리눅스 서버에 Docker 이미지·모델 파일 묶음을 옮겨 몇 개의 명령으로 설치·실행할 수 있다.
- 직원은 자체 계정으로 로그인해 PDF 업로드 → 질문 → 답과 원문 구간 확인을 웹에서 한다. 기관당 동시 사용은 5~10명을 기준으로 한다.
- 관리자는 웹 화면에서 계정을 관리하고 이용 기록을 조회한다.
- 이용 기록은 "누가 언제 무엇을 했는지"의 사실만 남기고 문서·질문·답변 내용은 남기지 않는다.
- 테스트 사이트와 설치판이 같은 PDF 처리·답변 코드를 공유한다.

## 비목표

- 행안부 근거 그래프 답변, 일반 대화, 공개 자료 검색(workspace), 기관 스냅샷 검색은 설치판에 넣지 않는다.
- 모델 품질 개선, 새 학습, 새 평가는 하지 않는다. 모델은 테스트 사이트의 Qwen3-1.7B 원본을 그대로 쓴다.
- AD/LDAP/SSO 연동은 하지 않는다(사용자 결정: 자체 계정).
- 질문·답변 원문 기록은 하지 않는다(사용자 결정: 이용 사실만).
- OCR(스캔 PDF), GPU 가속, 다중 서버 확장은 하지 않는다.
- 운영 중인 test.tridatum.co 배포 변경은 이 작업 범위가 아니다. 코드 공유로 테스트 사이트 코드는 바뀌지만, 재배포는 별도 결정이다.

## 반목표 (기술적으로 동작해도 실패인 것)

- 모델의 해설을 검증된 답처럼 보이게 하는 것. 현재처럼 원문과 글자 그대로 일치하는 문장만 "확인된 인용"이고, 나머지는 검증 안 된 해설로 표시한다. 모델 상태 문구("원본 모델(미특화) · 품질 기준 미달")와 한계 문구를 화면에 그대로 둔다.
- 설치·실행 중에 외부 네트워크로 무엇이든 보내는 것(모델 다운로드, 텔레메트리, 웹폰트, CDN 포함).
- PDF 본문·질문·답변이 디스크(로그, DB, 임시 파일, 컨테이너 레이어)에 남는 것.
- 한 직원의 문서·세션을 다른 직원이나 관리자가 볼 수 있는 것.
- 테스트 사이트의 기존 동작이 코드 이전 과정에서 조용히 바뀌는 것.

## 제약

- 저장소 관례: Python 3.12, 의존성 최소화와 오프라인 wheel 설치(`docs/SERVICE.md`), 버전 고정, 라이선스 명시.
- 실행 파일(모델 GGUF, llama-server, 업로드 토크나이저)은 Git에서 빠진 `runs/`에 있다. 이미지를 만들 때 sha256으로 고정해 포함한다.
  - 모델: `runs/open-weight-base/Qwen3-1.7B-Q8_0.gguf`, sha256 `061b54da…cb1a` (Apache-2.0)
  - 업로드 토크나이저: `runs/reader-factorial-01-cpt-v1-v2-v4/tokenizer.json`, sha256 `73551e65…b58d`
  - llama.cpp: 테스트 사이트와 같은 커밋 `8ca4060`을 리눅스 CPU용으로 빌드(MIT). 현재 바이너리는 맥 Metal 빌드라 그대로 쓸 수 없다.
- 현재 서버는 Cloudflare 앞단을 신뢰하는 구조다(`X-Trid-Proxy` 비밀 헤더, 고정 호스트 `test.tridatum.co`, `__Host-` 쿠키 → HTTPS 필수). 설치판에서는 이 인증을 자체 로그인으로 바꾸고 호스트명을 설정값으로 둔다.
- PDF 파싱은 별도 프로세스에서 15초 제한으로 실행된다(`scripts/shared_pdf_extract.py`). 메모리 512MiB 제한은 현재 macOS(`ps`)에서만 동작하므로 리눅스용으로 바꿔야 한다.
- 생성은 한 번에 하나(`state.work` 잠금). CPU 생성은 질문당 수십 초가 걸릴 수 있다.
- 기존 테스트: `tests/test_shared_demo.py`(66개), `tests/test_pdf_documents.py`, `tests/test_pdf_app.py`.

## 검토한 방식

| 방식 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A (선택)** | PDF 처리·답변 코드를 `trid/` 모듈로 옮기고 표준 라이브러리 HTTP 서버를 유지한다. 계정·세션·기록은 내장 SQLite, 비밀번호는 내장 scrypt를 쓴다. | 새 의존성이 없다. 테스트 사이트에서 검증한 CSRF·보안 헤더·크기 제한을 재사용한다. 저장소 관례와 같다. | 로그인·세션을 직접 구현하므로 보안 테스트를 꼼꼼히 해야 한다. |
| B | FastAPI 등 웹 프레임워크로 새로 작성한다. | 인증과 미들웨어 구조가 편하고 확장이 쉽다. | 오프라인 의존성과 라이선스 검토가 늘고, 기존 보안 처리를 새 구조로 다시 옮겨 검증해야 한다. |
| C | 앱은 그대로 두고 앞단 프록시가 로그인을 처리한다. | 앱 수정이 최소다. | 관리자 계정 관리 화면이 자연스럽지 않고, 이용 기록과 사용자 연결이 어색하다. 자체 계정 결정과 맞지 않는다. |

사용자가 **A**를 선택했다. 이유는 이미 동작하는 경로와 보안 처리를 재사용하고, 폐쇄망 의존성 부담을 피하기 위해서다.

## 결정된 내용

### 1. 기능 범위
- 직원 화면: 로그인 → PDF 업로드(1개, 텍스트 PDF) → 추출 문서 보기 → 질문 → 답(확인된 인용 + 검증 안 된 해설) + 원문 구간 → 자료 지우기 → 로그아웃.
- **모든 질문은 문서 검색 + `case` 모드로 처리한다(사용자 결정).** 테스트 사이트의 대화/검색 판단(`request_type`, `route`), `chat_reply`, 근거를 찾지 못했을 때 대화로 넘어가는 처리는 가져오지 않는다. 근거를 찾지 못하면 "찾지 못함"으로 끝난다.
- **질문은 하나씩 독립으로 처리한다(사용자 결정).** 대화 맥락(직전 메시지)은 모델에 넘기지 않는다. 화면에는 이 세션의 질문·답 목록을 보여 줄 수 있지만 서로 영향을 주지 않는다. 직원에게 "질문마다 완전한 문장으로 써 주세요"라고 안내한다.
- 답변 경로는 `answer_document_case`(`retrieve` → 문맥 맞춤 → 생성 → 인용 확인)를 테스트 사이트와 같은 코드와 같은 설정으로 쓴다.
- 기준 설정은 운영 중인 `deploy/macmini-site/versions.json`의 `trid-assistant-qwen3-1.7b` 항목이다(`case_system_512`, `max_tokens` 512, context 4096, greedy, 사고 모드 끔). *(내 판단)*
- *(내 판단)* 샘플 문서(`/api/sample`)와 텍스트 직접 입력(`/api/text`)은 뺀다. 샘플은 `data/`의 시연 자료에 의존하고, 용도가 PDF 확인이기 때문이다.

### 1-1. 업로드 한도 *(내 판단)*
- 처음 적은 20MB·80쪽은 잘못 적은 값이다. 테스트 사이트의 실제 한도는 요청 2MiB(`MAX_BODY`), 20쪽(`scripts/shared_pdf_extract.py`), 파싱 15초, 파싱 메모리 512MiB다.
- 설치판도 같은 한도로 시작하고, 한도를 설정값으로 둔다. 한도를 키우는 것은 설치판에서만 하며, 키울 때는 파싱 시간·메모리를 측정한 뒤 정한다. 공통 모듈은 한도를 인자로 받고, 테스트 사이트는 지금 값을 그대로 넘겨 동작이 바뀌지 않게 한다.

### 1-2. "같은 결과"의 기준 *(내 판단)*
- 같은 코드 경로, 같은 프롬프트 생성, 같은 디코딩 설정을 뜻한다. 맥 빌드와 리눅스 CPU 빌드의 생성 결과가 토큰까지 같다고 보장하지 않는다.
- 확인 방법은 두 가지다. ① 코드 이전 전후로 기존 테스트와 첨부 문서 경로 동작 고정 테스트(llama-server는 가짜 응답으로 대체)가 통과해야 한다. ② 배포 전에 리눅스 CPU 이미지에서 고정 PDF·질문 세트를 실행해 결과를 기록하고 사람이 확인한다. ②는 CI가 아닌 배포 전 점검이다.

### 2. 코드 구조 (방식 A)
- `shared_demo.py`에서 첨부 문서 경로에 필요한 부분(PDF 파싱 프로세스 실행, 청크 생성, 검색, `answer_document_case`와 그 보조 함수, llama-server 호출)을 `trid/` 아래 모듈로 옮긴다. 테스트 사이트는 그 모듈을 import한다.
- 옮기기 전에 기존 테스트가 통과하는지 확인하고, 옮긴 뒤 같은 테스트가 수정 없이 통과해야 한다. 필요하면 옮기기 전에 첨부 문서 경로의 동작 고정 테스트를 추가한다.
- 설치판 서버는 새 모듈(예: `trid/onprem/`)로 만든다. Cloudflare 신뢰 인증 대신 로그인 세션을 쓰고, 기존 보안 헤더·CSP·CSRF·요청 크기 제한·분당 요청 제한은 그대로 가져온다.

### 3. 로그인·권한 (사용자 결정: 자체 계정)
- 역할은 **사용자**(PDF 업로드·질문)와 **관리자**(사용자 기능 + 계정 관리 + 이용 기록 조회) 두 가지다.
- 첫 관리자는 설치할 때 컨테이너 안 CLI 명령으로 만든다. 이후 계정 생성·잠금·해제·비밀번호 초기화·역할 변경은 관리자 웹 화면에서 한다.
- *(내 판단)* 비밀번호는 scrypt 해시(개별 salt)로 저장한다. 5회 연속 실패하면 15분 잠긴다. 30분 동안 활동이 없으면 세션이 끝난다. 처음 로그인하거나 초기화된 뒤에는 비밀번호를 바꿔야 한다. 비밀번호는 최소 10자다.
- 업로드한 문서는 그 로그인 세션의 메모리에만 있고, 로그아웃하거나 세션이 끝나면 지운다. 관리자도 다른 사람의 문서를 볼 수 없다.

### 4. 이용 기록 (사용자 결정: 이용 사실만)
- 기록 항목: 시각, 계정, 접속 IP, 이벤트 종류(로그인 성공·실패, 로그아웃, 세션 만료, PDF 업로드, 질문, 자료 지우기, 관리자 작업), 결과(성공·오류 종류).
  - PDF 업로드: 파일 sha256, 쪽수, 처리 결과
  - 질문: 처리 시간, 결과 상태(답·근거 없음·오류)
  - 관리자 작업: 대상 계정, 작업 종류
- 파일명, 질문 원문, 질문 해시, 답변, PDF 본문, 원문 구간은 기록하지 않는다(파일명 제외는 사용자 결정. 파일명 자체가 민감할 수 있기 때문이다).
- 서버 표준 출력과 오류 로그에도 같은 기준을 적용한다. 예외 메시지나 traceback에 파일명·질문·본문이 들어가지 않게 한다.
- 관리자 화면에서 기간·계정·이벤트로 조회한다. *(내 판단)* CSV로 내보낼 수 있다. 보관 기간 기본값은 1년이고 설정으로 바꿀 수 있다(개인정보 접속기록 보관 관행 기준). 기록은 추가만 하고 웹에서 수정·삭제할 수 없다.

### 5. 패키징·설치
- docker compose 서비스 세 개:
  - `app`: 설치판 서버 + PDF 파싱. 계정·기록 SQLite는 볼륨에 저장한다.
  - `llm`: llama-server CPU 빌드 + GGUF 모델. 내부 네트워크에만 연결하고 외부로 포트를 열지 않는다.
  - `tls`: HTTPS 종료. 기관이 준 인증서를 쓰고, 없으면 설치할 때 자체 서명 인증서를 만든다.
- 전달물: 이미지 tar(`docker save`), compose 파일, 설정 예시(호스트명, 포트, 보관 기간), 한국어 설치·운영 안내서(설치, 첫 관리자 생성, 인증서 교체, 백업, 업그레이드, 사양), 구성요소 라이선스·sha256 목록.
- 대상 서버는 x86_64 리눅스, AVX2 이상 CPU다. llama.cpp는 빌드 컴퓨터 CPU에 맞춘 최적화(`GGML_NATIVE`)를 끄고 빌드한다. arm64는 지원하지 않는다. *(내 판단)*

### 6. 모델 정보 문구 *(내 판단)*
- 상태 "실험 서비스 · 원본 모델(미특화) · 품질 기준 미달", 기반 모델·revision·라이선스 표기는 `deploy/macmini-site/versions.json`의 문구를 그대로 쓴다.
- 설치판에서 사실이 아닌 표현(Metal 빌드, 맥미니 CPU, 공개 자료 검색, 모델의 대화/검색 선택)은 빼고 다음처럼 바꾼다. 측정 수치는 바꾸지 않는다.
  - 버전: "설치판 · Qwen3-1.7B 원본 가중치 그대로(튜닝 없음) · 올린 PDF에서만 근거 검색 · 질문별 독립 처리 · llama.cpp 8ca4060 리눅스 CPU 빌드 · greedy · 사고 모드 끔"
  - 한계: "올린 PDF에서 찾은 원문과 글자 그대로 일치하는 문장만 '확인된 인용'이며 해설은 검증하지 않았습니다. 관련도 상위 구간만 확인하므로 문서의 다른 부분에 정보가 없다고 보장하지 않습니다. 근거를 찾지 못한 질문에 기억으로 답하지 않습니다. 이미지·스캔 PDF는 읽지 못합니다."
  - 실측: 운영 항목의 `evaluation` 문구를 그대로 쓴다(이 서비스 조건 그대로의 측정은 없다는 내용 포함).

### 7. 동시 사용 (사용자 답: 기관당 동시 5~10명)
- 생성은 한 번에 하나다. 대기열 화면은 만들지 않는다. 다른 질문을 처리 중이면 짧게 기다린 뒤 "다른 질문을 처리 중입니다. 잠시 후 다시 시도해 주세요"를 보여 준다.
- *(내 판단)* 로그인 세션 상한은 32, 요청 슬롯은 8, 분당 요청 20회로 테스트 사이트 값을 그대로 쓴다. 생성 잠금을 기다리는 시간은 2초에서 늘릴 수 있다(빌더가 측정해 정한다).
- 안내서에 "동시 5~10명, 질문당 수십 초" 기준의 권장 사양을 적는다.

## 빌더에게 맡기는 것

- 새 모듈의 정확한 이름과 파일 나누기, SQLite 스키마.
- 리눅스에서 PDF 파싱 프로세스의 메모리 제한 방식(`RLIMIT_AS`, cgroup 등).
- TLS 컨테이너 종류(Caddy, nginx 등. 오프라인으로 동작하고 라이선스가 명확할 것).
- 관리자·로그인 화면 디자인. 기존 `trid/shared_ui`의 시각 언어를 따르고 외부 폰트나 CDN은 쓰지 않는다.
- 권장 서버 사양 측정과 안내서 표기(CPU 코어, 메모리, 질문당 시간).
- 생성 잠금 대기 시간과 대기 안내 문구의 세부(7절 범위 안에서).
- 첨부 문서 경로 동작 고정 테스트의 구체적인 사례 선정.
