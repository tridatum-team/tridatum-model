# 사내망 PDF 근거 확인 서비스 — Django 판 설계

작성일: 2026-11-13 · 상태: 사용자 검토 대기 (빌더 검토 반영)

## 의도

이미 만든 사내망 설치형 PDF 근거 확인 서비스(`trid/onprem`, 표준 라이브러리 HTTP 서버 + 정적 HTML/JS, 설계서 `docs/superpowers/specs/2026-11-13-onprem-pdf-web-design.md`)와 **같은 기능을 Django로 다시 만든 별도 프로젝트**를 같은 저장소에 둔다.

이유는 **앞으로 기능을 계속 붙이기 쉽게** 하기 위해서다(사용자 결정). 지금 판은 로그인·세션·잠금·CSRF·관리 화면·DB 스키마를 모두 직접 구현했다. 기능이 늘수록 이 직접 구현 부분이 부담이 된다. Django는 인증, 폼 검증, CSRF, DB 마이그레이션을 기본으로 갖고 있어서 새 기능을 이 위에 바로 얹을 수 있다.

기존 서비스는 그대로 둔다(사용자 결정). 두 판은 당분간 함께 있다.

## 목표

- 기존 판과 **같은 기능, 같은 규칙**을 Django로 제공한다. 기능과 규칙은 기존 설계서의 "결정된 내용" 1·1-1·3·4·5·6·7절과 그 뒤 반영된 수정 사항(아래 "기존 판에서 그대로 가져오는 규칙")을 따른다.
- 새 기능을 붙일 때 모델·폼·뷰·템플릿·마이그레이션이라는 Django의 표준 경로로 붙일 수 있는 구조를 만든다.
- 사내망 설치 방식은 같다. Docker 세 서비스(`app`, `llm`, `tls`), 443만 공개, 설치·실행 중 외부 연결 없음.
- 화면은 기존 판의 최신 디자인(두 칸 배치, Pretendard, 강조색 `#ffe14a`, 모델 정보 표)을 그대로 옮긴다.

## 비목표

- 기존 판(`trid/onprem`, `trid/onprem_ui`, `deploy/onprem`)을 바꾸거나 지우는 것.
- 기존 판의 계정·이용 기록을 새 판으로 옮기는 기능(사용자 확인: 아직 고객 설치가 없다).
- Django 기본 관리자 화면(`django.contrib.admin`)을 고객에게 여는 것.
- 외부 시스템용 API, AD/LDAP/SSO, 다중 서버·다중 프로세스 확장, OCR, GPU.
- 모델·답변 품질 변경. 답변 엔진 코드는 기존 판과 공유하고 고치지 않는다.

## 반목표 (동작해도 실패인 것)

기존 설계서의 반목표를 모두 그대로 적용한다. Django로 바꾸면서 특히 생기기 쉬운 실패는 다음과 같다.

- **업로드 PDF가 임시 파일로 디스크에 남는 것.** Django는 기본 설정에서 2.5MB가 넘는 업로드를 임시 파일에 쓴다.
- **파일명·질문·PDF 내용이 Django 로그나 오류 보고에 남는 것.** Django의 기본 로깅은 500 오류 때 요청 정보와 traceback을 출력하고, `DEBUG=True`면 화면에 노출한다.
- **문서·질문·답변이 세션 저장소(DB)에 들어가는 것.** Django 세션 데이터는 기본적으로 DB에 저장된다.
- **CDN의 htmx나 외부 글꼴을 불러오는 것.**
- **Django 관리자 화면이나 ORM을 통해 이용 기록을 수정·삭제할 수 있게 되는 것.** 보관 기간 정리(purge)만 예외다.
- 직원이 다른 직원의 문서를 보거나, 관리자가 직원의 문서를 보는 것.

## 제약

- Python 3.12, 버전 고정, 오프라인 wheel 설치(해시 고정), 라이선스 명시. 저장소 관례와 기존 판의 `deploy/onprem/requirements-app.txt` 방식을 따른다.
- 앱 이미지에는 torch·numpy가 없어야 한다(기존 판과 같은 빌드 검사).
- 답변 엔진과 PDF 처리 모듈은 기존 판과 **공유**한다. 복사하지 않는다: `trid/document_case.py`, `trid/pdf_isolated.py`, `trid/pdf_extract_worker.py`, `trid/pdf_documents.py`, `trid/llama_client.py`, `trid/prompts.py`, `trid/case_prompts.py`.
  - 모델 정보 문구는 `trid/onprem/model_card.py`의 `MODEL_CARD`를 가져다 쓴다.
  - PDF 추출 작업자는 `python -I`로 실행되므로 `trid`가 site-packages에 설치돼 있어야 한다(기존 판 결정 R3).
- 모델·토크나이저·llama.cpp는 기존 판과 같다. GGUF sha256 `061b54da…cb1a`, 토크나이저 sha256 `73551e65…b58d`, llama.cpp `8ca4060b7e30e76baaa5670ee1ec1b760b7f8552` CPU 빌드.
- 업로드한 문서는 **프로세스 메모리**에만 있다. 그래서 앱은 **프로세스 하나에 스레드 여럿**으로만 실행한다. 프로세스를 여러 개 띄우면 세션마다 문서가 다른 프로세스에 있게 되어 동작하지 않는다.
- 기관당 동시 5~10명, CPU 생성은 질문당 수십 초.

## 검토한 방식

| 방식 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A (선택)** | Django + 서버가 만드는 HTML 화면 + htmx(부분 갱신) | 인증·CSRF·폼·마이그레이션이 기본 제공. 새로 추가되는 Python 의존성이 적다(Django, asgiref, sqlparse, WSGI 서버). 언어 하나로 유지. | 원문을 끌어서 비교하는 것 같은 아주 복잡한 화면 상호작용은 번거롭다. |
| B | FastAPI(서버) + React(화면) | 풍부한 화면, 프론트엔드 분업이 쉽다. | Python·Node 두 도구 체계. 로그인·잠금·관리 화면·마이그레이션을 직접 고르고 짜야 한다. 오프라인 묶음 의존성이 가장 많다. |
| 제외 | Next.js 등 JS 프레임워크 | — | 답변 엔진이 Python이라 서버를 둘로 나눠야 한다. |

사용자가 **A**를 선택했다. 늘어날 기능이 주로 업무 기능(계정, 기록, 문서 종류, 설정)이라 Django 기본 기능 위에 가장 빨리 붙고, 사내망 의존성 부담도 가장 작다.

## 기존 판에서 그대로 가져오는 규칙

아래는 새 판이 반드시 같아야 하는 동작이다. 값은 기존 판 코드에서 확인한 것이다.

### 직원 기능
- 로그인 → PDF 업로드(1개, 텍스트 PDF) → 추출 문서 보기 → 질문 → 답(확인된 인용 + 검증 안 된 해설 + 원문 구간) → 자료 지우기 → 로그아웃.
- 모든 질문은 문서 검색 + `case` 모드로 처리한다. 질문은 하나씩 독립적으로 처리하며, 이전 질문을 모델에 넘기지 않는다. 안내 문구: "질문마다 완전한 문장으로 써 주세요. 이전 질문은 이어서 해석하지 않습니다."
- 답변 설정: family `qwen3`, context 4096, `max_tokens` 512, greedy, 사고 모드 끔.
- 답 결과 상태와 화면 표시는 기존 `trid/onprem_ui/app.js`의 `STATUS` 표를 그대로 쓴다. 상태는 `quoted`, `answer`, `unverified`, `review`, `not_found`, `clarify`, `model_failure`.
- 파일 이름은 브라우저에만 있고 서버로 보내지 않는다. 서버는 항상 `document.pdf`라는 이름으로 처리한다.
- 업로드 한도: 요청 2MiB, 20쪽, 50,000자, 파싱 15초. 설정으로 바꿀 수 있고, 화면의 한도 안내도 설정을 따른다.
- 질문 길이: 2,000자 이하.

### 계정·세션
- 역할은 직원(`user`)과 관리자(`admin`) 두 가지다.
- 5회 연속 실패하면 15분 잠긴다. 30분 동안 활동이 없으면 세션이 끝난다.
- 첫 로그인과 비밀번호 초기화 뒤에는 비밀번호를 반드시 바꾸게 한다. 비밀번호는 10자 이상 1024자 이하다.
- 아이디는 NFC 정규화, 앞뒤 공백 제거, 소문자로 바꾼 뒤 `[a-z0-9._-]{2,32}`여야 한다.
- 없는 아이디, 잠긴 계정, 비활성 계정은 모두 같은 오류 문구를 보여 준다("아이디 또는 비밀번호가 올바르지 않습니다."). 없는 아이디일 때도 실제 아이디와 같은 시간이 걸리게 가짜 해시 검사를 한다.
- 마지막 남은 활성 관리자는 비활성화하거나 직원으로 바꿀 수 없다.
- 비밀번호를 바꾸거나 초기화하면 그 계정의 다른 세션은 모두 끝난다.
- 첫 관리자는 컨테이너 안 명령으로 만든다(`create-admin`, `--password-stdin` 지원).
- 세션 상한 32, 요청 슬롯 8, 세션당 분당 요청 20회.

### 동시 사용
- 답변 생성은 한 번에 하나다. 기다려도 차례가 오지 않으면 503과 함께 "다른 질문을 처리 중입니다. 잠시 후 다시 시도해 주세요."를 보여 준다.
- PDF 읽기는 생성과 별도 잠금(동시 1개)이다. 대기 시간은 파싱 제한시간 + 2초다. 넘으면 "다른 문서를 읽는 중입니다. 잠시 후 다시 시도해 주세요."를 보여 준다.
- 모델 서버 토큰 계산 호출은 10초 제한이고, 생성 호출은 기존 판과 같은 제한을 쓴다.
- 답변이 끝난 시점에 세션이 무효가 됐으면(관리자가 비활성화·초기화) 답을 돌려주지 않고 401을 준다.

### 이용 기록
- 기록 항목: 시각, 계정, 접속 IP, 이벤트, 결과, 상세. 이벤트 종류는 기존 판 `trid/onprem/store.py`의 `EVENTS` 14가지(`retention_purge` 포함)다.
- 상세 키는 `sha256`, `pages`, `seconds`, `status`, `error`, `target`, `action`, `count`만 허용한다. 값은 `[A-Za-z0-9._:-]{1,128}`만 허용한다. 자유 문장이 기록에 들어갈 수 없게 하기 위해서다.
- 파일명, 질문, 질문 해시, 답변, PDF 본문, 원문 구간은 DB, 로그, 표준 출력, 오류 출력 어디에도 남기지 않는다.
- 관리자 화면에서 기간·계정·이벤트로 조회하고 CSV로 내려받는다. CSV는 UTF-8 BOM을 붙이고, 수식처럼 보이는 셀(`= + - @ \t \r`로 시작) 앞에는 `'`를 붙인다.
- 보관 기간 기본 365일(1 이상). 시작할 때 한 번, 이후 24시간마다 오래된 기록을 지운다. 웹에서 수정·삭제할 수 없다.

### 화면 문구와 모델 정보
- 모델 상태 문구 "실험 서비스 · 원본 모델(미특화) · 품질 기준 미달"을 그대로 항상 보이게 둔다.
- 모델 정보는 기존 판처럼 항목별 표로 보여 준다(모델, 상태, 구성, 기반 모델, 라이선스, 성능 측정, 한계).
- 오류 문구는 기존 판과 같은 한국어 문구를 쓴다. 예: 모델 서버 연결 실패 "모델 서버에 연결할 수 없습니다. 관리자에게 문의해 주세요."

### 보안
- 운영 쿠키는 `__Host-` 접두사, Secure, HttpOnly, SameSite=Strict다. 개발 모드(`--insecure-dev`에 해당)는 127.0.0.1에만 바인딩하고 Secure를 뺀다.
- 운영에서는 Origin이 `https://<hostname>`과 같아야 한다.
- 보안 헤더: CSP `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; frame-ancestors 'none'; object-src 'none'; base-uri 'none'; form-action 'self'`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store`. 글꼴 파일만 하루 동안 캐시한다.
- 접속 IP는 Caddy가 넣는 `X-Real-IP`만 믿는다.
- 로그인 실패 시 예외·traceback 대신 예외 종류 이름만 출력한다.

## 결정된 내용

### 1. 위치와 구성 *(내 판단)*
- 저장소 맨 위 `onprem_web/`에 Django 프로젝트를 둔다. 설정 모듈은 `onprem_web/settings.py` 하나다. Django 앱은 역할별로 나눈다.
  - `accounts`: 사용자 모델, 로그인·로그아웃·비밀번호 변경, 잠금, 세션 정책.
  - `workspace`: 직원 화면, PDF 업로드, 질문, 자료 지우기, 세션별 메모리 문서 저장소, 생성·파싱 잠금.
  - `audit`: 이용 기록 모델(추가만 가능), 조회, CSV, 보관 기간 정리.
  - `staffadmin`: 한국어 관리자 화면(계정 관리, 이용 기록).
- 배포 파일은 `deploy/onprem_web/`에 둔다. 모델 서버 이미지(`deploy/onprem/Dockerfile.llm`)와 Caddy 설정은 기존 판 것을 그대로 쓰거나 참조한다. 앱 이미지·compose·번들 스크립트·안내서는 새 판용으로 만든다.
- 문서는 `docs/ONPREM_WEB.md`(설치·운영 안내, 한국어)에 둔다.

### 2. 의존성 *(내 판단)*
- Django 5.2 LTS(2028년 4월까지 보안 지원)와 그 의존성(asgiref, sqlparse), WSGI 서버 하나, 그리고 기존 판과 같은 tokenizers·pypdf. 모두 버전과 해시를 고정한다.
- WSGI 서버는 **프로세스 하나, 스레드 여럿**으로 돌릴 수 있는 것을 쓴다(제약 참고). 빌더가 gunicorn(`--workers 1 --threads N`)과 waitress 중 오프라인 설치·라이선스·스레드 동작을 확인해 고른다.
- htmx는 정해진 버전 하나를 파일로 저장소에 넣어 같은 출처에서 제공한다(CDN 금지). eval이 필요한 기능은 끈다.
- Django 추가 패키지(django-axes, django-csp 등)는 쓰지 않는다. 잠금과 CSP는 작은 자체 코드로 처리한다. 의존성을 줄이기 위해서다.

### 3. Django 기본값에서 반드시 바꿀 것 *(내 판단)*
- `DEBUG=False`(개발 모드만 예외), `ALLOWED_HOSTS=[hostname]`, `CSRF_TRUSTED_ORIGINS=["https://hostname"]`.
- 업로드: 임시 파일 핸들러를 쓰지 않는다. 메모리 업로드 핸들러만 쓰거나 요청 본문을 직접 읽는다. 요청 크기 상한은 설정값을 따른다.
- 로깅: `django.request`, `django.server`, `django.security` 로거가 요청 내용이나 traceback을 내보내지 않게 한다. 오류는 예외 종류 이름만 한 줄로 남긴다. 관리자에게 오류 메일을 보내지 않는다.
- 세션: DB 세션을 쓰되, 세션 데이터에는 사용자 식별과 정책 값(비밀번호 버전, 마지막 활동 시각 등)만 둔다. 문서·질문·답은 세션에 넣지 않고 메모리 저장소에 세션 키로 둔다. 쿠키 이름은 운영 `__Host-trid`, 개발 `trid-dev`다.
- `django.contrib.admin`은 설치하지 않는다. `django.contrib.messages`처럼 사용자 입력을 저장할 수 있는 기능은 쓰지 않는다.
- 비밀번호 해시는 Django의 scrypt 해셔를 쓴다. 최소 길이 검증은 10자다.
- 이용 기록 모델은 수정·삭제를 막는다(`save`·`delete` 제한). 보관 기간 정리 명령만 일괄 삭제한다.
- 정적 파일: CSS·JS·htmx·글꼴은 앱이 직접 제공한다. 글꼴은 하루 캐시하고, 나머지는 `no-store`다.

### 3-1. DB와 이용 기록 보호 *(내 판단)*
- DB는 SQLite 하나이고 `data_dir`(컨테이너의 `/data`) 아래에 둔다. 새 판은 빈 DB로 시작한다. WAL 모드와 바쁠 때 대기 시간(busy timeout)을 켜서 스레드 여럿이 함께 쓸 수 있게 한다.
- 이용 기록은 모델의 `save`·`delete` 제한에 더해 **DB 트리거**로 막는다. `UPDATE`는 항상 거부하고, `DELETE`는 보관 기간 정리 명령이 켜는 표시가 있을 때만 허용한다. `QuerySet.update`·`bulk_update`처럼 모델 메서드를 거치지 않는 경로도 막기 위해서다. 트리거는 마이그레이션으로 만든다.

### 3-2. 기존 판과 다를 수 있는 보안 세부 *(내 판단)*
- 기준은 **기존 판의 동작**이다. Django 기본값과 다르면 기존 판에 맞춘다.
- `__Host-trid` 쿠키는 `Path=/`이고 `Domain`이 없어야 한다.
- CSRF는 Django CSRF 미들웨어를 쓰되 기존 판과 같은 모양으로 맞춘다. 토큰은 세션에 두고(`CSRF_USE_SESSIONS`, 별도 CSRF 쿠키 없음), 페이지의 `<meta name="csrf-token">`으로 내려 주며, htmx·JSON 요청은 기존 판과 같은 `X-Trid-Token` 헤더로 보낸다(`CSRF_HEADER_NAME`). 배포 전 점검 스크립트가 쿠키 하나와 이 헤더만 쓰기 때문이다. Origin 검사는 기존 판처럼 운영 `https://<hostname>`, 개발 `http://127.0.0.1:<port>`와 정확히 같아야 한다.
- 세션이 끝나면(로그아웃, 30분 경과, 관리자 비활성화·초기화, 비밀번호 변경, 세션 상한 정리) 그 세션 키의 메모리 문서도 함께 지운다. DB 세션이 지워졌는데 메모리 문서만 남는 일이 없게, 메모리 저장소도 주기적으로 정리한다. DB에는 남았는데 메모리 문서가 없는 경우(앱 재시작)는 "문서를 다시 올려 주세요"로 처리한다.

### 3-3. JSON API *(내 판단)*
- 직원 화면은 htmx로 HTML 조각을 받지만, 기존 판과 같은 **JSON API도 함께 둔다**: `/api/login`, `/api/logout`, `/api/password`, `/api/load`, `/api/ask`, `/api/clear`. 경로, 요청·응답 JSON 형태, 오류 코드와 문구가 기존 판과 같다.
- 이유는 두 가지다. 배포 전 점검 스크립트(`deploy/onprem/release_check.py`)를 그대로 공유할 수 있고, 두 판의 결과를 같은 JSON으로 비교하는 테스트가 가능해진다. 앞으로 기능을 붙일 때도 화면과 API가 같은 서비스 함수를 쓰게 된다.
- 구조: 업무 로직은 뷰가 아닌 서비스 함수(예: `workspace/services.py`의 `load_pdf`, `ask`)에 두고, 이 함수가 결과 dict를 돌려준다. htmx 뷰는 이 dict로 템플릿을 그리고, JSON 뷰는 그대로 돌려준다.
- 관리자 기능은 htmx 화면만 둔다. 이용 기록 CSV 주소(`/api/admin/events.csv`)는 기존 판과 같게 둔다.

### 3-4. 기존 판과 같은 서버에 함께 띄우기 *(내 판단)*
- 한 서버에는 **한 판만 설치한다.** 둘 다 443 포트와 모델 서버를 쓰기 때문이다. 같은 서버에 둘을 띄우면 CPU와 메모리를 나눠 써서 답이 느려진다.
- 다만 빌드 머신에서는 둘을 함께 빌드하고 시험할 수 있게 이름을 나눈다. compose 프로젝트 이름은 `trid-onprem-web`, 앱 이미지 태그는 `trid-onprem-web-app`이다. 모델 서버와 Caddy 이미지는 기존 판 것을 그대로 쓴다.

### 4. 화면
- 기존 판 화면(직원·관리자·로그인)을 Django 템플릿으로 옮긴다. 레이아웃, 문구, `common.css`, Pretendard 글꼴은 그대로 가져온다.
- 동작은 기존 판처럼 페이지를 새로 고치지 않고 부분만 바뀐다. 업로드 결과, 답, 계정 표, 기록 표를 htmx로 갱신한다. 답 화면 구성(확인된 인용, 인용 앞뒤 원문, 검증 안 된 해설, 자료 한계, 상태 표시)은 기존 `app.js`의 `renderAnswer`와 같은 내용을 서버 템플릿에서 만든다.
- 브라우저에서 처리해야 하는 것은 작은 자체 JS로 남긴다. 파일 이름 표시, 업로드 크기 사전 확인, 글자 수 표시가 해당한다.

### 5. 명령
- `python -m onprem_web serve --config /data/onprem.json [--insecure-dev]`, `create-admin`, `purge`. 기존 판과 같은 이름과 옵션이다. 설정 파일 형식도 기존 판 `onprem.json` 키를 그대로 쓴다.
- 시작할 때 토크나이저 sha256을 검사한다. 운영에서는 다르면 거부하고, 개발 모드에서는 경고만 한다(기존 판 R11).
- DB 마이그레이션은 `serve`가 시작할 때 자동으로 적용한다. *(내 판단: 설치·업그레이드 단계를 줄이기 위해서다. 안내서에 적는다.)*

### 6. 패키징·설치
- compose 서비스 세 개는 기존 판과 같은 구조다. `app`만 새 이미지이고, `llm`·`tls`는 기존 판과 같은 설정이다.
- 기존 판의 보안 결정을 그대로 적용한다.
  - 앱 이미지: `python -I`로 실행, 작업 폴더 `/`, read-only, cap_drop ALL, uid 10001.
  - 의존성: `--no-deps --require-hashes`로 설치하고, 기반 이미지 digest를 기록한다.
  - Caddy: `ocsp_stapling off`, 자체 로그를 남기지 않음, `X-Real-IP` 설정, 업로드 크기는 `TRID_MAX_BODY`로 조절.
  - 로그: 크기 제한과 개수 제한으로 순환한다.
  - `.dockerignore`는 허용 목록 방식이다.
- 번들 스크립트와 안내서는 새 판용으로 만든다. 배포 전 점검(`deploy/onprem/release_check.py`)은 3-3절의 JSON API 덕분에 그대로 공유한다.

### 7. 테스트와 "같은 동작"의 기준 *(내 판단)*
- 완료 기준은 **전체 이전**이다. 위 "기존 판에서 그대로 가져오는 규칙"이 모두 들어가고 각각 테스트가 있어야 한다. 직원 화면만 먼저 만드는 뼈대 수준이 아니다(사용자 요청: 기능 똑같이).
- 위 "기존 판에서 그대로 가져오는 규칙"의 각 항목마다 새 판에도 테스트를 둔다. 기존 판 테스트(`tests/test_onprem_*.py`)의 시나리오를 기준 목록으로 쓴다.
- 답변 엔진은 공유하므로, 같은 가짜 모델 응답이면 같은 결과가 나와야 한다. 두 판에 같은 가짜 응답을 넣고 `/api/ask` 결과 JSON이 같은지 비교하는 테스트를 둔다(3-3절의 JSON API 사용).
- 배포 전 점검 스크립트 `deploy/onprem/release_check.py`가 새 판에도 수정 없이 돌아가야 한다.
- 기존 판의 테스트와 동작은 바뀌지 않아야 한다(기존 `test_onprem_*` 127개 통과 유지).
- 새 판 테스트도 저장소 관례대로 `tests/` 아래에 두고 `unittest`로 돌린다. Django 테스트 러너가 필요하면 그 방법을 안내서와 테스트 파일 머리에 적는다.

## 빌더에게 맡기는 것

- Django 앱 안의 파일 나누기, 모델 필드와 마이그레이션 세부.
- WSGI 서버 선택(2절 조건 안에서)과 스레드 수.
- htmx 버전과 부분 갱신의 구체적인 요청·응답 형태.
- 잠금·세션 상한·분당 요청 제한을 미들웨어와 뷰 중 어디에 둘지.
- 관리자 화면 표·폼의 구체적인 마크업(기존 판 디자인을 유지하는 범위 안에서).
- 기존 판과 공유할 수 있는 배포 파일(Caddyfile, `Dockerfile.llm`, `make_self_signed.sh`, `release_check.py`)을 복사할지 참조할지.
